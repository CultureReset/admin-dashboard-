Building the Node

How to build the system, and how every part of it stays separated per person. Isolation is the one property you cannot add later — this is the shape it has to have from the first commit.

Companion to Open Glasses Spec Boundaries 9 Isolation tests 10
01

Scope from commit 1 Non-negotiable

The single most expensive migration in software is adding tenancy to a system that did not have it.

You will build V1 for yourself. One person, one pair of glasses, one node. It is very tempting to skip person scoping until there is a second user — and it is the mistake that ends up rewriting every query, every storage path, every cache key and every test you wrote in between.

The rule

Every table has person_id. Every blob path is prefixed by person. Every capability call runs inside a person context. Every cache key includes person. From the first commit, with one user.

It costs you about a day up front. Retrofitting it costs months and leaks data in the meantime.

The corollary matters just as much: person is never a function parameter. It is ambient context established once, at the device session, and read by every gate below. The moment an app can pass a person id, isolation becomes a code review problem instead of a structural one — and code review does not scale to a third-party app store.

02

Identity model

Five entities. Getting the cardinalities right settles most of the design.

EntityIsCardinalityOwns
NodeOne installation. A household or a business.1Hardware, models, shared config
PersonA human with data on the nodeN per nodeTheir data, keys, policy, app instances
DeviceGlasses, pendant, speaker, car moduleN per person, or sharedNothing. Devices are stateless (spec §3.1).
Identity nodeAn Android handset holding one person's loginsExactly 1 per person. Never shared.Sessions and credentials for that person
App instanceAn installed app, scoped to one person1 per (app, person)Its own private storage

2.1  Shared devices need a rule

A kitchen speaker is not bound to a person. It has to acquire person context per request — an explicit claim ("it's Matt"), or voice identification. Until it has one:

Default for unbound devices

A device with no person context gets household scope only. It can answer general questions and read explicitly shared data. It cannot read anything person-scoped. No exceptions, no "probably Matt" heuristics — a wrong guess reads someone else's private data aloud in a shared room.

2.2  Genuinely shared data

Some rows really are household-wide: the family shopping list, the thermostat, the door lock. Model this explicitly with a scope column rather than by leaving person_id null, which turns "unowned" and "shared" into the same bug.

-- scope is explicit; the default is always private
scope        text not null default 'person',   -- person | household
person_id    uuid not null,                  -- creator, even when shared
household_id uuid not null

04

Data Build first

Row-level security, forced, with person context set by the host and never by the caller.

4.1  Why row-level and not schema-per-person

ApproachBlast radiusMigrationsShared rowsVerdict
Row-level + RLSOne policy bug exposes everythingOne migrationNaturalRight for a household node
Schema per personContainedN migrations, driftAwkwardOnly past ~50 people
Database per personTotalN databases to operateCross-person is a join across databasesOnly for business tenants

Row-level is right here — but it is only safe if the policy is forced and the runtime role is not the table owner. Both defaults work against you.

4.2  The pattern

-- once per table. No exceptions — §15 has a CI check that enforces this.
alter table observation enable row level security;
alter table observation force  row level security;   -- applies to the owner too

create policy person_isolation on observation
  using (
    person_id = current_setting('app.person_id')::uuid
    or (scope = 'household'
        and household_id = current_setting('app.household_id')::uuid)
  );

And the only place person context is ever set — inside the capability host, per transaction:

begin;
  set local role app_runtime;            -- never the owner, never superuser
  select set_config('app.person_id',    $1, true);   -- true = LOCAL
  select set_config('app.household_id', $2, true);
  -- the app's query runs here, and cannot see past the policy
commit;
The classic bug

Never use SET without LOCAL. A non-local setting survives the transaction and, behind a connection pooler, is inherited by the next person's request on that connection. This is the single most common multi-tenancy data leak, and it is silent — every test passes, because tests rarely run two people through one pooled connection.

Two more rules that keep this honest:

  • The runtime role owns nothing and can create nothing. Migrations run as a separate role.
  • No raw SQL crosses the capability boundary. Apps get typed capability calls; the host writes the SQL. Spec §13 of your architecture doc already requires this — RLS is the second line, not the first.
05

Blobs and keys Build first

Path separation is bookkeeping. Key separation is what makes deletion real.

node-store/
  person_4a1f/            // prefix per person — necessary, not sufficient
    obs/2026/08/30/<uuid>.jpg.enc
    obs/2026/08/30/<uuid>.opus.enc

5.1  Two-level keys

KeyScopeStoredPurpose
DEKOne per objectWrapped, beside the objectEncrypts the blob
KEKOne per personOS keychain / Secure EnclaveWraps every DEK for that person
Why this is the whole game

Deleting a person means destroying one KEK. Every wrapped DEK becomes undecryptable instantly — including in backups, offsite copies, and snapshots you cannot reach into.

DELETE FROM cannot do this. Backups are exactly where "delete my data" quietly fails, and cryptographic erasure is the only mechanism that actually reaches them.

On a Mac mini the KEKs live in the Keychain, unlocked once at boot. That is a real operational constraint worth stating: an unattended reboot leaves the node unable to decrypt anything until someone unlocks it. Either accept that, or store the KEKs in a hardware token that survives reboot — and understand that the second option means a stolen node is a stolen archive.

06

Apps After V1

Third-party code on a machine holding someone's entire life needs a sandbox, not a code review.

OptionIsolationCostVerdict
Manifest only, no codeTotalTrivialRight for V1's three apps
WASM moduleSandboxed by constructionA host runtime to buildRight for the app store
Container per appKernel-level, escapableHeavy on a Mac miniOnly if apps need real runtimes
Node process, reviewedNone. Full filesystem and network.NoneNever for third parties

WASM is the answer for third-party apps. A module has no ambient authority at all — no filesystem, no sockets, no clock beyond what you hand it. The capability API is the only import, which means the sandbox boundary and the permission boundary are the same line of code instead of two things that have to agree.

app instance = (app_id, person_id)          // two people, two isolated instances
  ├── imports: capability calls only        // no WASI fs, no sockets
  ├── storage: kv scoped to (app_id, person_id)
  └── limits:  memory cap · fuel budget · wall-clock deadline

The fuel budget matters more than it looks: without it, one badly written app pins a core and every other person on the node waits behind it. Isolation is a performance property too.

07

Inference Build first

The boundary people forget. One model server, several people's prompts.

Sharing model weights across people is fine and necessary — you are not loading a 4B model five times. What must not be shared is context, retrieval and cache.

ThingShared?Rule
WeightsYesOne process, one queue. No isolation concern.
RetrievalNeverScoped to person before it reaches the model. The model has no ambient data access — it receives context, it never fetches it.
Prompt / KV cacheConditionallyKey by the exact token prefix and nothing else. Identical prefix means identical content, so a hit cannot leak. Keying on anything coarser — a session id, a truncated hash — can.
System promptConditionallyIf it embeds personal context it is person-specific by definition. Never build one that mixes people.
Adapters / fine-tunesNeverA per-person LoRA is person data. Load it under person context or not at all.
The way to think about it

The model is a pure function. Everything person-specific arrives as an argument and nothing persists between calls. If you can state that truthfully about your inference layer, this boundary holds. If the model can reach out and fetch something, it does not.

08

Sessions and devices Build first

Where person context is born. Everything downstream inherits whatever this gets right or wrong.

8.1  Pairing binds, sessions carry

pairing   (once)   device attests → operator confirms → device_id ↔ person_id, persisted
session   (per connect)  attested key → token { device_id, person_id, exp: minutes }
request   (per call)     token → person context → every gate below reads it

8.2  Presence is a security control

The nose-bridge presence sensor from spec §14 is not only a battery saver. Glasses removed means the session suspends; putting them back on requires re-auth through the companion phone. Without it, a pair of glasses left on a table is a permanent, unattended identity for whoever picks them up — and unlike a phone, glasses have no lock screen.

8.3  Identity nodes

The Android handset holding a person's real logins is the highest-value target on the network. Two rules, both structural:

  • The device is looked up from the session's person, never passed as an argument. There is no code path where an app names which handset to drive.
  • ADB keys live in a per-person keystore on the node and never leave it. Apps call identity.act({provider, intent, args}) and never learn a device exists.
09

Network and egress

9.1  Devices cannot address each other

# one key per device; AllowedIPs restricts what each can reach
[Peer]  # glasses, person A
PublicKey  = …
AllowedIPs = 10.8.0.11/32        # the node only. Not 10.8.0.0/24.

A compromised pair of glasses should reach the node and nothing else — not the other devices, not the household LAN, and certainly not the identity nodes.

9.2  Segment the identity nodes

Five Android handsets logged into banks and retailers belong on their own VLAN, reachable only from the node. They are the one part of this system where a compromise is directly monetisable.

9.3  Egress

  • Redaction runs before the send, as a pipeline stage, and writes what it stripped back onto the observation (spec §9.2).
  • Per-person API keys where the provider supports them. Household billing is a convenience; a business tenant will require it for audit, and retrofitting per-person keys means re-plumbing every provider adapter.
  • Every external call writes an audit row: person, app, destination, bytes, what was redacted. That table is the receipt in spec §8, and it is worth more to a user than any toggle.
10

One request, six gates

Person context is established once and read everywhere. No gate accepts it as an argument.

Traced concretely, a "what is that?" from Matt's glasses:

1  device connects        attested key → known device_id
2  session bind           device_id → person_id (from pairing) → token, 15 min
3  policy gate            person's compiled bundle says: image → external OK, redact EXIF
4  capability host        set local app.person_id; token scope checked
5  store gate             insert observation → RLS stamps and filters by person
                          blob written to person_4a1f/…, DEK wrapped by Matt's KEK
6  egress                 image redacted, sent, audit row written under person_4a1f

Nowhere in that trace does any component take a person as a parameter. Delete step 2 and the whole chain fails closed, which is the property you want.

11

The capability host Build first

One module. Every read and write in the system goes through it. Build this before any app.

This is the door your architecture doc §13 describes, made concrete. It is the only component that holds a database connection, the only one that touches blob storage, and the only one that can reach an identity node. If a second component grows a database connection, the design has already failed.

// the shape every capability has — no exceptions
async function invoke(ctx, capability, args) {
  assertToken(ctx.token, capability);        // scope + expiry (spec §8)
  assertPolicy(ctx.policy, capability, args); // per-element, may redact (spec §9)

  return withPersonContext(ctx.person, async (tx) => {
    const result = await HANDLERS[capability](tx, args);
    await audit(tx, ctx, capability, args);  // same transaction as the effect
    return result;
  });
}

Two details that are easy to get wrong and expensive to fix later:

  • ctx.person comes from the session, not from args. There is no code path that reads a person from arguments. Enforce it with a type: the handler signature simply has nowhere to put one.
  • The audit row is written in the same transaction as the effect. Otherwise a crash between them produces an action with no receipt, which is the one failure mode that destroys trust in the whole privacy story.
12

Delete and export

Two operations that prove the isolation model is real rather than aspirational.

12.1  Delete a person

1  revoke every session and capability token
2  wipe and unenrol their identity node
3  destroy the KEK            ← every blob, live and backed up, is now unreadable
4  delete rows under person_id
5  write a tombstone: who, when, what scope. Keep the tombstone.

Step 3 is what makes the rest honest. Steps 1, 2 and 4 are reversible from a backup by anyone with the tape; step 3 is not reversible by anyone, which is the point.

12.2  Export a person

Data portability is not a compliance checkbox here — it is the product claim. Section 16.2 of the spec argues you sell sovereignty, and sovereignty you cannot leave with is a slogan.

export/person_4a1f/
  observations.jsonl       // decrypted, with provenance intact
  entities.jsonl
  media/                   // decrypted blobs
  apps/<app_id>/kv.json    // per-app state
  policy.json
  audit.jsonl              // what left, and when
A test worth writing early

Export a person, delete them, import into a fresh node, and confirm the system behaves identically. If that round trip works, your separation is genuine — because nothing of that person was entangled in shared state. If it does not, the export is telling you exactly where the leak is.

13

Repo layout

One repo. The boundaries in §3 should be visible in the directory tree, not just in the prose.

proto/            // device protocol schema, versioned. Shared by firmware and node.
  ogp-1.json      // JSON Schema for every verb + capability descriptor (spec §3)

firmware/         // ESP32-S3. Capture, compress, encrypt, route. Nothing else.

node/
  gateway/        // WebSocket server, device sessions, attestation, pairing  ← §8
  policy/         // compile bundles, distribute to edges, evaluate            ← §9
  router/         // classify once, dispatch directly, speculate (spec §7.2)
  capabilities/   // THE ONLY MODULE WITH A DB CONNECTION                     ← §11
  store/          // migrations, RLS policies, blob adapter, key management   ← §4, §5
  pipeline/       // stt / vision / tts adapters. Pure functions.             ← §7
  identity/       // android node control, per-person keystores               ← §8.3
  wasm-host/      // app sandbox and fuel budgets                             ← §6

apps/             // first-party apps. Same capability API third parties will get.
sdk/              // app-facing SDK. Compiles to the WASM import surface.
companion/        // phone app: hotspot, GPS, identity, offline fallback brain
shell/            // display renderer for framebuffer-class devices (spec §10)
One lint rule worth having on day one

Fail the build if anything outside node/capabilities/ and node/store/ imports the database client. It is three lines of config and it prevents the single architectural decay that ruins systems like this — a "quick" direct query from the router that becomes forty of them.

Build order

Spec §17 with the isolation work folded in. Each phase is usable and each needs the one before it.

#PhaseIncludes the isolation workDone when
0Schema and host Every table with person_id, RLS forced, the CI check from §15, the capability host, per-person KEKs Two seeded people exist and neither can see the other, proven by test
1Gateway and pairing Device attestation, session tokens, the bind that creates person context A device pairs to a person and a forged token is rejected
2Pipeline, no device Person-scoped retrieval; cache keys include person Curl an image and a question, get spoken audio back, under 1.2 s
3Firmware Nothing new — the device holds no state by design Tap, speak, hear the answer. Measured, 20 times.
4The three apps Capability tokens with real scopes; first policy bundles "What is this", "Remember this", "Add to my list" all work
5Second person The moment of truth. Everything above already assumed this. Two pairs of glasses, two people, zero code changes
6Identity node Per-person keystore, VLAN, identity.act audit trail An app action runs as the right person and cannot reach the other
7Offline path Companion queues writes with idempotency keys Unplug the node mid-request; nothing is lost or doubled
8Display Nothing new — display.card() is a capability like any other Text in the lens, and the same call speaks on a device without one
Phase 5 is the checkpoint that matters

If adding the second person requires any schema change, any new parameter, or any "just for now" special case, phases 0–4 were built wrong and this is the cheapest moment you will ever have to find out. Add a second seeded person in phase 0 and keep them there — an empty second account in every test run is what stops the whole thing quietly becoming single-tenant.

15

Isolation tests Non-negotiable

Isolation rots silently. These are the tests that make it fail loudly instead.

#TestGuards
1For every table, B's context cannot read, update or delete any of A's rows. Generated from the schema, so new tables are covered automatically.§4
2CI fails if any table lacks enable and force row level security, or lacks a person_id column.§4
3Two people's requests interleaved through one pooled connection never see each other's rows. Run it with a pooler, not a direct connection.§4 — the SET LOCAL bug
4No capability handler signature can accept a person identifier. Enforced by type, checked by a compile-time test.§11
5Destroying A's KEK makes every A blob undecryptable — including from a restored backup taken before the deletion.§5, §12
6An app installed by A and B has two isolated KV namespaces; a write in one is invisible in the other.§6
7A WASM app cannot open a socket, touch the filesystem, or exceed its fuel budget — and exhausting fuel kills only that instance.§6
8A shared device with no person context reads household-scoped rows only, and gets an explicit refusal for anything person-scoped.§2.1
9Revoking a capability token takes effect on the next call. Presence "removed" blocks calls until re-auth.§8
10Export A, delete A, import into a fresh node: identical behaviour, and A's data is gone from the original.§12

Tests 2 and 3 are the two that pay for themselves. Test 2 stops the slow decay where someone adds a table in a hurry; test 3 catches the pooled-connection leak, which no ordinary test suite reproduces because ordinary tests run one person at a time.

Do not build yet Deliberately deferred

Each of these is a real product. None of them is on the critical path to proving the architecture.

DeferredWhyBuild it when
App storeThe WASM host, review, signing and distribution are a quarter of work that proves nothing about the architectureYour own three apps have run for a month and the capability API has stopped changing
Third-party devicesThe protocol has to stop moving before anyone can implement itYou have shipped two device types yourself
World-locked ARNeeds a local GPU and asynchronous timewarp — a different product (spec §10.3)Head-locked has proven people want a display at all
Cellular in the glassesCarrier certification, antennas, another subscription, more batteryNever, probably. The phone is already an excellent modem.
Continuous recordingIncompatible with every wearable power budget (spec §9.3)A tethered or desk device wants it
Node-to-node federationSharing between households multiplies every boundary in §3One node works for several people first
Hosted nodesTurns nine boundaries into nine boundaries plus a compliance surfaceYou know whether people will run their own
What the whole thing rests on

Two people, two pairs of glasses, one node, three apps, and a test suite that proves neither person can reach the other. Everything in the deck — the app store, third-party hardware, displays, external models — is addition on top of that. Nothing above it is architecture.
