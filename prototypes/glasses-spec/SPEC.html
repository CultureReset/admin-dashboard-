01

Decisions locked Decided

Settled in review. Rationale recorded so they can be revisited on evidence, not memory.

1.1  Wi-Fi only. No BLE.

One radio, one stack, WebSocket end to end. The usual objection is that BLE is needed for a milliwatt-class always-on control channel — but on an ESP32-S3, Wi-Fi modem-sleep with DTIM3 averages 1–2 mA, which is the same order as a maintained BLE connection at this duty cycle. You delete an entire protocol stack and pay almost nothing.

What you give up: BLE proximity pairing, so "connects automatically when near your phone" has to come from mDNS discovery plus a saved network instead. Acceptable.

Consequence: deck slide 2 collapses from two planes to one. See §15.

1.2  One Android device per person, physically attached to the node.

The home node is shared compute and shared storage. Identity is not shared. Each person gets a dedicated Android device holding their own logged-in sessions, so accounts never mix and the system can act as that person in apps that have no API. Full treatment in §6.

1.3  The glasses are not a Raspberry Pi.

Forced by §11. The Pi Zero 2 W has no suspend-to-RAM, so it cannot be duty-cycled — it either runs continuously or cold-boots for 20+ seconds. Running continuously needs 104 g of battery. This is the single most consequential finding in the document.

1.4  The display capability is semantic, never a framebuffer.

Devices receive display.card(), not pixels. One call, many renderers — green text on a waveguide or a full framebuffer on birdbath optics. §10.

02

The thesis

What is actually being built, stated so it fits on one line.

The product

A device protocol and a private node. Any hardware that implements the protocol gains the entire app ecosystem; the node owns the data and decides where computation happens. The glasses are the reference implementation, not the product.

This matters because it determines what is defensible. Not the Pi, not the Sony sensor, not the frames — all replaceable within a year. What is defensible is the protocol third parties build against and the data model their apps depend on. Ship those wrong and every device becomes a special case in the router; ship them right and someone else can build a pendant, a helmet, a car module or earbuds and inherit everything.

The deck currently has an app protocol (slide 6) but no device protocol. That is the largest gap in it, and §3 fills it.

03

Device Protocol v1 Spec

Ten verbs, a capability descriptor, and a versioned handshake. Everything else is built on this.

3.1  Design rules

  1. Semantic, never raw. Devices receive intent (display a card, speak this), never pixels or PCM buffers. This is what lets a 40-character monochrome HUD and a 1080p birdbath display satisfy the same call.
  2. Devices declare, the router adapts. No device is assumed to have a camera, a screen, or a speaker. The router reads the capability descriptor and degrades accordingly.
  3. Devices are dumb and stateless between requests. All persistent state lives on the node. A device that loses power and reboots rejoins with no local recovery.
  4. Every message is versioned and cancellable. Both from day one, or you can never change anything and you leak in-flight work forever.

3.2  Transport

WebSocket over TLS, inside a WireGuard tunnel, one persistent connection per device. The device dials out; the node never dials in. That means no inbound firewall rules, no NAT traversal, and the same code path whether the device is on home Wi-Fi or tethered to a phone on cellular.

# at home                     # away
device → LAN → node          device → phone hotspot → WireGuard → node

At home the phone drops out of the path entirely and the system works with the internet disconnected. That property is worth a slide of its own — it is the strongest argument the architecture has, and it is currently absent from the deck.

3.3  Handshake and capability descriptor

First message after connect. The router caches this and uses it for every routing decision afterwards.

{
  "proto": "ogp/1",
  "device": {
    "id": "dev_8f21c0",          // stable, factory-assigned
    "kind": "glasses",           // glasses | pendant | vehicle | speaker | watch
    "make": "acme", "model": "v1",
    "firmware": "0.4.1"
  },
  "capabilities": {
    "capture":  { "still": true, "video": false,
                   "max": [2304, 1296], "fov": 78, "indicator": "hardwired" },
    "listen":   { "channels": 2, "rate": 16000, "wakeword": true, "vad": true },
    "speak":    { "codecs": ["opus"], "transducer": "bone" },
    "display":  { "class": "text",       // none | text | rich | framebuffer
                   "cols": 40, "rows": 5, "mono": true, "anchor": ["head"] },
    "location": { "source": "companion" },  // none | onboard | companion
    "sensor":   { "imu": true, "presence": true, "tap": true }
  },
  "limits": { "uplink_kbps": 8000, "max_payload_kb": 512 }
}

display.class is the field that makes §10 work. A device answering "none" simply never receives display calls, and the router falls back to speech — no special-casing anywhere else in the system.

3.5  The same interface on three devices

This is the payoff. One app, no branching.

An app that asks for display gets text on the glasses, speech on the pendant, and a full card on the dash — because it asked semantically. That is the whole argument for §3.1 rule 1.

3.6  Versioning Spec

  • proto is ogp/<major>. A node must accept every major version it has ever supported, or you break deployed hardware you do not control.
  • New capability fields are additive and optional. Absent means unsupported.
  • New verbs require a major bump. Devices reject unknown verbs with {"error":"unsupported_verb"} rather than failing the connection.
  • Devices never auto-upgrade protocol version. The node negotiates down to the device.
04

The Observation Spec

The core datatype. It appears in your architecture doc only as a word inside an example — everything else depends on it.

Section 8 of the architecture doc gives the right instinct — "you don't want an AI model being your database; the AI should operate on the database" — and then illustrates it with a query against observations. That table is never defined anywhere. It is the thing every capture produces, every app reads and every memory query runs against. Define it once, here, or every app invents its own shape.

4.1  Schema

create table observation (
  id             uuid primary key,
  person_id      uuid not null,          -- whose observation, always
  device_id      text not null,          -- which device produced it
  captured_at    timestamptz not null,
  received_at    timestamptz not null,   -- differs when queued offline

  -- what was captured
  kind           text not null,          -- image | audio | text | sensor | composite
  media_ref      text,                   -- pointer into object storage, never inline bytes
  media_sha256   text,
  transcript     text,                   -- if audio was transcribed
  description    text,                   -- if vision described it

  -- where and how
  location       geography(point),
  location_acc_m real,
  heading_deg    real,

  -- provenance: which model said the description, so it can be re-run later
  derived_by     jsonb,                  -- {"vision":"qwen3-vl-4b@q4","stt":"whisper-small"}
  confidence     real,

  -- policy travels with the row, it is not looked up later
  policy         text not null,          -- local | node | private_cloud | external
  retain_until   timestamptz,            -- null = keep; camera mode sets this at capture
  redactions     text[],                 -- fields stripped before any egress

  -- linkage
  request_id     uuid,                   -- the interaction that produced it
  entity_ids     uuid[]                  -- structured entities resolved from it (§5)
);

create index on observation (person_id, captured_at desc);
create index on observation using gist (location);
create index on observation (retain_until) where retain_until is not null;

4.2  The four rules that make it work

  1. Policy is a column, not a lookup. Every row carries the policy it was captured under. If the user tightens their settings tomorrow, yesterday's rows keep the promise made when they were taken. Re-deriving policy at query time is how privacy systems leak.
  2. Retention is set at capture. The camera mode (§9.3) writes retain_until when the row is created. A nightly job deletes expired rows and their media. "Keep locally for 24 hours" is one column, not a subsystem.
  3. Media is referenced, never embedded. Rows stay small enough to scan; blobs live in object storage and are deleted by the same retention job.
  4. Provenance is mandatory. derived_by means a better model can re-describe old observations later, and a wrong answer is traceable to the model that gave it.
Why this makes memory work

"Where did I see those shoes yesterday?" becomes a SQL query — person, time window, description match, ordered by location — not a prompt against a model's recollection. The embedding is an accelerator on top, never the source of truth. That distinction is the difference between a system that remembers and one that confabulates.

4.3  Who may write one Spec

Only the capture pipeline. Third-party apps read observations through a capability and may annotate them by creating entities that reference them — they may never insert or mutate an observation row. An app that could forge an observation could forge your memory.

06

Identity and Android nodes Decided

One shared brain, one private identity per person. This solves multi-user and the no-API problem at once.

6.1  The problem it actually solves

Two problems, and it is worth being clear that they are separate:

  1. Multi-user. One node, several people. Sessions, lists and memories must never mix. Binding identity to a physical device makes the boundary obvious and auditable rather than a row-level-security policy someone has to get right.
  2. No API surface. Most of what people actually want done has no API — a specific retailer, a loyalty account, a utility, a bank. A logged-in Android running the real app is a universal adapter for exactly those.
The objection to answer first

"Why not use the person's own phone? It is already logged into everything." Because the phone is with them, asleep, or out of signal. The dedicated device exists to act unattended — overnight, while they are driving, while the phone is in a pocket. If you never need unattended action, you do not need this and slide 3's phone is enough. Decide that deliberately; it removes five devices from the bill of materials.

6.2  Why physical devices, not virtual ones

Your instinct here is right, and the reason is not performance:

  • Container Android cannot run on macOS. Waydroid and redroid need Linux kernel binder and ashmem modules. A Mac mini cannot provide them at any price.
  • The Android emulator will not hold sessions. AVDs run fine on Apple Silicon, but Play Integrity fails on emulated and rooted devices. Banking, retail and streaming apps — exactly the ones with no API, exactly the ones you need — detect this and refuse.
  • Stock, unrooted, physical devices pass. That is the whole reason to buy hardware.

So the architecture is a Mac mini for shared compute and storage, plus N cheap physical Android handsets, one per person.

6.3  Wiring: skip the splitter

You mentioned needing a splitter. You probably do not.

ApproachProsConsVerdict
Powered USB hub + ADBRock solid, survives reboots, devices always chargedNeeds a powered hub (5 phones draw 10 W+); cable sprawl; permanent charging kills batteriesWorkable
ADB over Wi-FiNo hub, no cables, devices can sit anywhere, charge on a scheduleadb tcpip needs re-enabling after a device reboot — script itRecommended
The failure nobody plans for

Lithium cells held at 100% charge at room temperature swell within about a year. Five phones trickle-charging 24/7 on a hub is five swollen batteries and five replacements. Either use devices with a hard charge cap (Samsung's "Protect battery" holds at 85%; Sony exposes real limits) or put the hub on a switched schedule that cycles them between 40% and 80%. Budget for this or it becomes a recurring surprise.

6.4  Control stack

node
 ├── adb            // device lifecycle, install, shell
 ├── scrcpy         // mirror + inject input when a human needs to look
 └── companion app  // resident agent on each device, HTTP on localhost
        ├── native path   → the app's own API/intent where one exists
        └── fallback      → UiAutomator2 / Appium when it does not

Write the companion app. Driving everything through screen automation is brittle and slow; driving it through Android intents and app APIs where they exist, with UiAutomator only as a fallback, is the difference between a demo and something that survives an app update.

6.5  Security boundary Spec

The Android node holds a person's real credentials. It is the highest-value target in the system, so it sits behind the capability layer like everything else:

// what an app may call
await sdk.identity.act({ provider: "retailer.example",
                          intent:   "cart.add",
                          args:     { sku: "…" } });

// what an app may never reach
adb -s <device> shell …          // raw device access: node-internal only
  • An Android node serves exactly one person_id. Never two.
  • Third-party apps get identity.act with a named provider and intent, scoped by capability token (§8). They never learn the device exists.
  • Every identity.act writes an audit row. This is the receipt that makes §8 real.
  • The node's ADB keys never leave the node.

6.6  Honest limits

  • Five is fine. Fifty is a device farm. Past roughly a dozen you need racks, monitoring, per-port power control and someone whose job this is.
  • The Mac mini is a good node with one real gap: no CUDA. MLX runs a 4B VLM well on Apple Silicon, and idle draw is 5–10 W, which is excellent. But most inference tooling is CUDA-first, so you will be on the less-travelled path for anything beyond llama.cpp and MLX. 16 GB handles a 4B VLM at Q4; plan 32 GB+ if you want headroom.
  • App updates break screen automation. Assume the fallback path needs maintenance every few months. This is a real operational cost, not a one-time build.
Open decision

Does an Android node act only on explicit request, or does it run background automations on a schedule? The second is far more useful and considerably more dangerous — an unattended device logged into someone's bank, acting on a cron. Decide before building §6.4.

07

The router Fix

Slide 4's best line is "an action router, not just a model router." Its architecture as drawn defeats its own privacy claim.

7.1  Split the router in two

Slide 4 draws the gateway as a box between the phone and the node. Either way that is drawn, it fails:

  • If it is a separate device, it is a second single point of failure in a system that already has one.
  • If it runs on the node, then a request that must never leave the device has already left the device in order to be told to stay local.

Standard policy-engine architecture solves it: one decision point, many enforcement points.

NODE                        compiles policy  ──┐
                                               │  signed policy bundle,
                                               │  pushed on change
   ┌───────────────────────────────────────────┴──────────────┐
   ▼                        ▼                                 ▼
GLASSES                  PHONE                             NODE
evaluates locally        evaluates locally                 evaluates locally
before any egress        before any egress                 before any egress

Policy flows outward; data does not flow inward to be judged. Slide 4 should show both arrows.

7.2  Route directly. Do not climb.

Both the deck and the doc describe escalation as a ladder — try local, if unsure try the node, if still unsure try the cloud. Each rung costs a full round trip, so the requests that need the most help are punished the most. Architecture doc §6 has three sequential model calls in its worked example.

Instead: classify once at the edge, dispatch directly.

utterance ──▶ classifier (edge, ~15 ms)
                │  keyword match + small embedding lookup
                │  over registered app intents and device commands
                ▼
        ┌───────┴────────┬─────────────┬──────────────┐
        ▼                ▼             ▼              ▼
   L0 device cmd    L1 edge model  L3 node       L4 external
   (no model)                                    (if policy allows)

For the genuinely ambiguous middle, run speculatively: fire at the node while the edge classifier is still deciding, and cancel (§3.4) the loser. You pay a little wasted compute to remove a round trip from the critical path — which is the correct trade, because compute is cheap on the node and latency is expensive on someone's face.

7.3  Routing inputs

Slide 4 lists five. Add a sixth, and give the fifth an output path.

Capability tokens Spec

Slide 6 is the deck's strongest slide. It grants booleans where it needs to grant scoped, expiring tokens.

"User approved once" becomes ambient authority forever. A permission checkbox at install time cannot express "while the app is in the foreground", "for this request only", or "until Tuesday" — and those are the grants people actually want to give.

{
  "iss": "node:matt",
  "sub": "app:plant-identifier",
  "person": "person_4a1f",
  "scope": ["camera.still.on_request", "observation.read.own"],
  "constraints": {
    "foreground_only": true,
    "max_calls": 1,
    "egress": "node"          // this app may not reach external models
  },
  "exp": 1756400000            // seconds, not months
}

8.1  Rules

  • Every capability call carries a token. No token, no call — there is no ambient path.
  • Tokens are minted per grant and expire. Long-lived grants are refreshed, not permanent.
  • Just-in-time consent: an app may request a capability mid-session and the user answers then, in context, the way iOS does. Install-time is the worst moment to ask.
  • Revocation is immediate and takes effect on the next call, not the next launch.
  • Every call writes an audit row: app, scope, person, timestamp, destination.
The feature that actually builds trust

Not the toggle — the receipt. "This week: 14 requests to an external model, 3 to Maps, 0 images sent, 2 identity actions." A single "Internet ✓/✕" switch on slide 7 gets flipped on during setup and never looked at again. A weekly ledger gets read.

Policy routing Fix

Slide 7's slider is the best concept in the deck. Its granularity is wrong, and your own example proves it.

9.1  One request, several policies

"Add this to my Christmas list" contains two data elements with opposite requirements:

A single all-or-nothing slider cannot express this. Policy must be evaluated per data element, strictest element wins for the request as a whole, and the router must be able to redact and downgrade — send the image externally while everything else stays home.

This is the genuinely novel part

"Split the request and route the parts differently" is what makes this architecture different from a model router with a privacy checkbox. Right now the slide undersells it as a choice between four settings. Redraw it as a request being decomposed, each part taking a different exit.

9.2  Redaction is a pipeline stage, not a policy

element ──▶ policy check ──▶ redactors ──▶ egress

                              ├── face blur / person removal
                              ├── OCR scrub (cards, screens, documents)
                              └── record what was stripped → observation.redactions

Writing the redaction list back onto the observation matters: it is how you later prove what left, and how a re-run against a better model knows what it never saw.

10.2  The API is the same either way

This is the whole point of §3.1 rule 1. One call, two renderers, chosen from capabilities.display.class:

await sdk.display.card({
  title: "Bald Eagle",
  body:  "Haliaeetus leucocephalus",
  meta:  "92% confidence",
  ttl:   4000,
  anchor: "head"
});

// class:"text"        → 3 lines of green text, ~40 cols
// class:"framebuffer" → rendered by the shell, full layout
// class:"none"        → falls back to speak(), no app change

Your architecture doc already reserved display() in the §25 device protocol, even though §16 defers displays to a later version. Those reconcile cleanly: V1 devices may implement display() as a no-op. State that explicitly or implementers will assume it is mandatory.

10.3  The constraint that needs its own slide

Head-locked works remotely. World-locked does not.

A panel that floats at a fixed spot relative to your head tolerates 80 ms of latency — nothing needs to stay pinned to the world, so remote rendering is fine and your redirect works exactly as it does for the shell.

A label that sticks to the actual building needs motion-to-photon under ~20 ms. No cloud round trip achieves that, ever. The fix is asynchronous timewarp: render remotely at whatever latency, then reproject locally against the newest IMU pose in the final ~2 ms before scanout. That needs a local GPU — a phone or a Pi 5 can, an ESP32 cannot.

So add a rule to the execution ladder on slide 8: anything in the motion-to-photon path never leaves the device, even when its content came from Level 4. Rendering is a Level 0 concern regardless of where the words came from.

V1 is head-locked. World-locked AR is a different product with a local GPU in it.

Power budget Decided

The missing slide the whole deck rests on. Assumptions: 16 waking hours, 30 queries per day, 87% conversion efficiency, ~20 g per 1000 mAh including protection.

For scale: Ray-Ban Meta is about 50 g in total, frames included. Anything over roughly 70 g on the bridge of your nose becomes uncomfortable inside an hour.

11.1  Why the Pi cannot be duty-cycled

The obvious rescue for configuration A is to sleep the Pi between queries. It does not exist.

  • Raspberry Pi has no suspend-to-RAM. Not on the Zero 2 W, not on any model — the GPU firmware does not support it. There is an experimental firmware project targeting 2–5 mA suspend with sub-second wake, but nothing has been validated on hardware.
  • Cold boot is 20–30 seconds, or 8–10 with an aggressively stripped image. Either is unusable as a per-query wake.
The finding

The Pi Zero 2 W is disqualified not because it draws too much power, but because it cannot be turned off between queries. That forces continuous operation, which forces 104 g of battery, which is twice the total weight of a finished pair of consumer glasses.

Slide 1's "powers the glasses for all-day use" is off by roughly an order of magnitude, and slides 2 and 3 inherit the assumption.

11.2  What this changes

Your architecture doc already argued the right case in §1 — "keep them deliberately stupid: capture, compress, encrypt, route" — and then specified a Linux SBC. Those four verbs are an MCU job. The Pi is the one component that contradicts the document's own thesis, and the power budget is what settles it.

Configuration C is the design: an ESP32-S3, a text HUD, a ~400 mAh cell, ~25 hours of runtime, under 10 g of electronics and battery. Everything the deck asks the glasses to do — capture, listen, speak, trigger, display — fits inside it.

The three moves that buy 1.7 seconds

1. Everything that can start on the tap, starts on the tap — radio, capture, upload, vision encode. The 1.5 seconds someone spends saying "add this to my Christmas list" is free transfer window.

2. STT and vision are independent. Fork them; the diagram should show a fork that rejoins at intent, not a chain.

3. Speak before the write confirms. If the write fails, correct it — that is rarer than the 40 ms is common.

Hard requirement

These numbers assume a GPU on the node. A 4B VLM on CPU answers in seconds to tens of seconds — fine for batch, useless with someone waiting. An M-series Mac with unified memory qualifies; a CPU-only mini does not.

The row worth putting on a slide

At home with the internet down, everything still works. No cloud relay, no external dependency, full personal context. That is the single most persuasive property this architecture has over every commercial pair of glasses, and it is currently nowhere in the deck.

13.1  Two rules that make degradation usable

  • Always say which level answered. "I'm offline from your node, so this is a general answer" is a good product. Silently downgrading and sounding equally confident is not.
  • Queue writes, never drop them. Every write travels with an idempotency key so a reconnect cannot double-add an item to a list.

16

Positioning

Two claims to change before either document goes to anyone else.

16.1  Sell sovereignty, not savings

Architecture doc §21 argues the home node "centralises the expensive computer." For a household with several devices, partly true. For one person with glasses and a phone it is a new cost: a capable node is $400–1500 of GPU plus 100–200 W of always-on power, against compute in a phone they already own and already paid for.

Doc §22 already has the better line — "your platform doesn't sell intelligence, it sells orchestration." Lead with that. You own the data, you choose the model, you can leave. Pitching cost reduction invites an arithmetic argument you lose; pitching ownership is an argument no incumbent can answer.

16.2  The schema boundary in your own codebase Fix

Doc §13 is correct that third-party apps must never get schema access — capabilities only, never INSERT INTO.

But the dashboard in this repository works on the opposite principle. From its README: "it asks the database what tables exist… and turns every table that has data into a section." Schema reflection is its entire design — add a table, a section appears.

Do not share this code

Both patterns are right in their own context: a first-party dashboard over your own data can safely reflect schema; a third-party app store absolutely cannot. But they are opposite trust models, and reusing the discovery code from one in the other hands developers exactly the SQL surface §13 forbids. Write the boundary down before any code moves between them.

17.3  Six decisions still open Open

  1. Unattended identity actions. May an Android node act on a schedule, or only on explicit request? (§6.6)
  2. iOS or Android first for the companion, given iOS's background constraints. (§15)
  3. Do you need identity nodes at all in V1, or is the person's own phone enough until unattended action matters? (§6.1)
  4. Default policy for a new user: node-only, or external-allowed with redaction?
  5. Retention default for on_demand captures — keep forever, or expire?
  6. Does the node ship as hardware you sell, software people install, or a hosted node they can migrate off? This one decides the business, not just the architecture.
