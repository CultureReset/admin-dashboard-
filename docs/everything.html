CyberCheck Business Dashboard — how it works

A dashboard where every business gets sections built from their own data, with nothing hardcoded per business or per industry.

1. The idea in one paragraph

Every business is identified by a slug (flora-bama-yacht-club). Everything about that business lives in tables that carry an entity_slug column. The dashboard doesn't have a list of features — it asks the database what tables exist, pulls the rows belonging to that slug, and turns each table that has data into a section. A restaurant ends up with Menu, Hours, Happy Hour. A charter ends up with Trips, Species, Meeting Points, Weather Rules. Same code. Different data.

Add a table to the database → it appears in every business that has data in it. Drop a table → the section disappears. No deploy, no code change.

2. Why this matters

The alternative is writing a component per feature and a dashboard per industry. That doesn't scale: the database currently has 305 tables carrying a slug (174 with data today), and the schema is still growing. Hardcoding even the current set would mean rewriting the app every time the schema moves.

This approach also means all ~4,020 existing businesses have a working dashboard immediately — their data is already in the database, so there is nothing to set up.

3. How a dashboard gets built, step by step

  sign in (slug + password)
          │
          ▼
  who is this?  ──────────────►  entity_owners  (or platform_admins for staff)
          │                       server-side, cannot be faked from the browser
          ▼
  read the live schema  ───────►  PostgREST OpenAPI spec
          │                       every table with an entity_slug column
          ▼
  sweep those tables  ─────────►  SELECT * WHERE entity_slug = <slug>
          │                       ~305 requests, 12 at a time, streamed in
          ▼
  discover sections  ──────────►  every table that came back with rows
          │                       becomes one section
          ▼
  render  ────────────────────►  purpose-built component if one exists,
          │                       otherwise the universal renderer
          ▼
  edit  ──────────────────────►  form built from that table's columns
                                  writes scoped to this business's slug

Two data sources are merged: the GCR API (/api/gcr/entity/:slug) supplies a rich, pre-joined payload for the ~60 tables it knows about (menu sections with their items already nested), and the direct table sweep covers everything else. Where both have the same table, the API version wins because it arrives better shaped.

4. The files that matter

The engine — src/lib/

FileWhat it does
schemaDiscovery.jsAsks the database what tables exist, every load. Finds every table with an entity_slug column. This is why new tables appear automatically. Also extracts each table's columns, which is how edit forms build themselves.
entityTables.jsSweeps those tables for one slug. Runs 12 at a time, streams each result back the moment it lands, caches per business. Tables blocked by permissions return nothing and quietly drop out.
discoverSections.jsTurns raw results into sections. Decides what counts as data, gives each table a human label and icon, merges the API payload with the swept tables.
gcrApi.jsThe two GCR API calls: fetch one business by slug, and search businesses by name.
writeEntityData.jsEvery write goes through here. Forces the business's own slug onto inserts; filters updates and deletes by slug as well as row id, so a tampered id can't reach another business.
AuthContext.jsxSign in, session, and access. Resolves which business you are from entity_owners, and admin status from platform_admins — both server-side.
supabaseClient.jsSupabase connection (URL + public key).
format.jsMoney, times, day names.

The screens — src/pages/

  • Login.jsx — sign in with the business slug and a password.
  • Dashboard.jsx — orchestrates everything: fetch, sweep, discover, render.
  • BusinessPicker.jsx — admin only. Searchable list of all businesses; click one to open its dashboard.

Layout — src/components/

  • TopBar.jsx — business name, sign out, and the admin banner when staff are viewing someone else's dashboard.
  • BottomNav.jsx — one tab per discovered section. Mobile-first; there is no sidebar.
  • MainContent.jsx — content area and empty state.
  • RowEditor.jsx — builds a form from a table's columns. Numbers get number inputs, dates get date pickers, booleans get yes/no, long text gets a textarea. A table added tomorrow gets a working editor with no new code.

Sections — src/sections/

  • GenericSection.jsx — the important one. Renders any table by inspecting the shape of its rows: finds the title-ish field, the description-ish field, the price-ish field, shows the rest as small labelled chips so nothing is silently dropped. This is what makes unknown tables work.
  • EditableSection.jsx — wraps any section with Add / Edit / Delete.
  • registry.jsx — a small map of purpose-built renderers for cases where the generic layout isn't good enough (day-of-week mapping, image grids, nested price tiers, star ratings). This does not define which sections exist — discovery does. Anything not listed here falls through to GenericSection.
  • The rest (HoursSection, MenuSection, PhotosSection, …) are those purpose-built renderers.

Scripts — scripts/

provision-accounts.mjs — creates a login for every active business.

SUPABASE_SERVICE_KEY=<service_role key> node scripts/provision-accounts.mjs --dry-run --limit=5
SUPABASE_SERVICE_KEY=<service_role key> node scripts/provision-accounts.mjs

For each business it creates a Supabase Auth account (login = the slug), writes the ownership row into entity_owners, and appends credentials to business-credentials.csv. Safe to re-run — existing accounts are skipped. Unique password per business by default.

Only 100 of 4,020 businesses have a real email, so logins use a derived address (<slug>@biz.gulfcoastradar.com) that never receives mail. The business types their slug; the app maps it to that address behind the scenes.

make-setup-links.mjs — generates a one-time link letting a business set their own password and add a real email. Text or email it to them. The script only produces links; it sends nothing.

SQL — sql/

Neither file has been run. They are proposals for you to review.

ownership_and_write_access.sql — required before editing works for real:

  1. Locks entity_owners so nobody can grant themselves ownership
  2. Creates platform_admins + is_platform_admin() for staff access
  3. Creates owns_entity(slug) — passes for the owner or an admin
  4. Enables owner-scoped write policies on 8 starter tables, keeping public read intact so GCR Unified is unaffected
  5. Notes the open anon write grants and two tables leaking secrets (below)
  6. The one-liner to make yourself an admin

Without it: entity_owners stays empty, so nobody can sign in to a business; platform_admins doesn't exist, so admin access never engages; and edits fail with permission errors.

entity_sections.sql — optional. One read-only function that returns all of a slug's data in a single call instead of ~305 requests. Respects existing permissions exactly; adds no new exposure.

5. Running it

npm install
npm run dev      # http://localhost:5173
npm run build    # production build into dist/

Deploy dist/ anywhere static (Vercel, Netlify).

Admin deep link. From CyberCheck login admin, link each business row to:

https://<dashboard-host>/?business=<slug>

That drops you straight into that business's dashboard with full edit rights and an "Admin view" banner. With no ?business= parameter, admins land on the searchable business list instead.

6. Security model

ConcernHow it's handled
Which business am I?Read from entity_owners in the database. Not from browser-writable metadata — that was the original design and it was unsafe: anyone could have pointed themselves at any slug.
Can I edit someone else's data?Every write is filtered by your own slug in the client, and the database enforces it independently through row-level security. Both halves are required; the client half alone is not security.
Admin accessChecked against platform_admins server-side. Nobody can self-promote from the browser.
Table permissionsTables locked by row-level security return nothing and simply don't appear. No special-casing.

Three pre-existing issues in the database, found while building this

Not caused by this project — worth fixing regardless:

  1. anon holds INSERT/UPDATE/DELETE on every table by default, and ~46 slug tables have row-level security switched off. Anyone with the public key (which sits in your public site's JavaScript) can modify them.
  2. bookable_resources has a public-read policy exposing wifi_password and ical_export_token.
  3. song_requests has a public-read policy exposing fan_phone.

Fixes are sketched in section 5 of ownership_and_write_access.sql.

7. Honest status

Verified: builds clean; section discovery tested against realistic payloads (a restaurant and a charter produce completely different, correct section sets from identical code); all database facts confirmed by direct query.

Never run: this app has not been opened in a browser, has not authenticated against Supabase, has not fetched a live business, and has not saved an edit. The build environment had no network access to Supabase or the GCR API, so every runtime path is unproven. Treat it as unrun code until it's deployed.

Not built yet:

  • Composio connections — connecting HubSpot, Salesforce, Facebook, Gmail.
  • The modular-app framework — installable apps like Song Requests, Tips, Waivers, plus the SDK third parties would build against. There is no app concept in this code at all.
  • AI data routing — describing what you want to add in plain words and having it land in the right table.
  • Known gap: a section only appears when its table already has rows, so a business with no menu can't create their first menu item. Needs an "add a section" flow listing tables they don't use yet.

8. Suggested order of work

  1. Deploy it and sign in as one real business. Nothing else is meaningful until the read path is proven against live data.
  2. Run ownership_and_write_access.sql, then provision accounts with --limit=5 and confirm sign-in works.
  3. Fix the empty-table gap so businesses can add their first row of anything.
  4. Build the modular-app framework.
  5. Add Composio connections alongside apps, so the store reads as one catalog.
  6. Add AI data routing on top.

What can be taken from two open-source projects, what it maps to in our database, and what is genuinely new versus already covered.

MIT means: copy, modify, ship commercially, keep changes closed. The only obligation is preserving the copyright notice and license text wherever substantial code is copied verbatim. Porting a schema design carries no obligation at all — designs aren't copyrightable — but crediting both projects is the decent thing to do.

What each project actually is

OpenSyteRentTools.io

Star counts mislead here. RentTools has fewer stars but far more commits and is actually deployed and in use. OpenSyte is broader but earlier.

Two things neither project gives you

1. Neither ends OTA fees. RentTools reads calendars from Airbnb, Booking and Vrbo so a host can see everything in one place. It has no booking engine, no checkout and no payment models. To take direct bookings you still need: availability display → booking form → Stripe Connect capture → confirmation. That work is ours, on top of bookings, entity_bookings and booking_calendar, which already exist.

2. Neither can be adopted wholesale. Both are Next.js + Prisma with their own schema and tenancy. Ours is Vite + Supabase, everything keyed by entity_slug across a 563-table database that also feeds GCR and GCR Unified. Taking either platform means two schemas, two auth systems, two sources of truth — the exact opposite of the model everything else depends on.

So: port the designs, not the platforms.

Gap B — platform defaults. Their CalendarPlatform is a registry with per-platform default buffers, colour, icon, and import/export instruction keys (so the UI can tell a host how to get their Airbnb iCal URL). Our booking_platform has the identity fields but none of the presentation or guidance.

ALTER TABLE public.booking_platform

  ADD COLUMN IF NOT EXISTS icon_url text,
  ADD COLUMN IF NOT EXISTS default_buffer_before smallint NOT NULL DEFAULT 0,

2.1 Workflow engine — the main lift

Their model, condensed: a Workflow owns WorkflowNodes connected by WorkflowConnections, fired by a WorkflowTrigger, producing a WorkflowExecution with per-node NodeExecution rows and an ExecutionLog. Actions are separate typed tables (EmailAction, SmsAction, WhatsAppAction, SlackAction, CalendarAction).

Minimum viable port — four tables rather than their eleven:

CREATE TABLE IF NOT EXISTS public.workflows (
  id           uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  entity_slug  text NOT NULL REFERENCES public.entity(slug) ON DELETE CASCADE,
  name         text NOT NULL,
  description  text,
  status       text NOT NULL DEFAULT 'draft'
               CHECK (status IN ('draft','active','paused')),
  trigger_type text NOT NULL,       -- e.g. 'booking.created', 'schedule.daily'
  trigger_config jsonb NOT NULL DEFAULT '{}'::jsonb,
  graph        jsonb NOT NULL DEFAULT '{}'::jsonb,  -- nodes + connections
  created_at   timestamptz NOT NULL DEFAULT now(),
  updated_at   timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX ON public.workflows (entity_slug);

CREATE TABLE IF NOT EXISTS public.workflow_runs (
  id           uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  entity_slug  text NOT NULL REFERENCES public.entity(slug) ON DELETE CASCADE,
  workflow_id  uuid NOT NULL REFERENCES public.workflows(id) ON DELETE CASCADE,
  status       text NOT NULL DEFAULT 'running'
               CHECK (status IN ('running','succeeded','failed','cancelled')),
  trigger_data jsonb,
  started_at   timestamptz NOT NULL DEFAULT now(),
  finished_at  timestamptz,
  error        text
);
CREATE INDEX ON public.workflow_runs (entity_slug, started_at DESC);

CREATE TABLE IF NOT EXISTS public.workflow_run_steps (
  id           uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  run_id       uuid NOT NULL REFERENCES public.workflow_runs(id) ON DELETE CASCADE,
  node_id      text NOT NULL,
  step_order   smallint NOT NULL,
  status       text NOT NULL,
  input        jsonb,
  output       jsonb,
  error        text,
  started_at   timestamptz,
  finished_at  timestamptz
);

CREATE TABLE IF NOT EXISTS public.workflow_logs (
  id           uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  run_id       uuid NOT NULL REFERENCES public.workflow_runs(id) ON DELETE CASCADE,
  level        text NOT NULL DEFAULT 'info',
  message      text NOT NULL,
  details      jsonb,

Nodes and connections go in workflows.graph as JSON rather than their own tables — simpler to start, and the editor works on the whole graph anyway. Split them out later if graph-level querying is needed.

TemplatePackage → TemplateVersion → TemplateInstallation → TemplateShare is an install/version/share mechanism, and it maps almost directly onto modular apps that third parties can build and distribute.

2.3 App contract

VariableDefinition + ActionTemplate describe how an action declares its inputs. Rather than porting the tables, fold this into app_versions.manifest — a JSON contract per version:

{
  "app_key": "song-requests",
  "tables": ["song_requests", "songs"],        // data it owns, slug-keyed
  "dashboard": { "route": "/apps/song-requests", "label": "Song Requests" },
  "public": { "type": "form", "path": "/r/:slug/request" },
  "permissions": ["read:entity", "write:song_requests", "send:sms"],
  "events": { "emits": ["request.created"], "consumes": ["payment.received"] },
  "settings": [
    { "key": "min_price", "type": "number", "label": "Minimum request", "default": 5 }
  ]
}

This is what an SDK targets, and what the dashboard reads to know where to mount the app.

2.4 Secondary lifts

  • Invoicing — Invoice, InvoiceItem, Payment are gateway-agnostic (method enum plus gatewayId), so Stripe Connect drops in. Useful for platform billing and for businesses invoicing their own customers.
  • CSV import — ImportSession, ImportTemplate, ImportRow, ImportRowIssue give column mapping, saved mappings, dedupe modes and per-row error reporting. Better than the import flow in cybercheck-login.
  • UI components — Shadcn + Tailwind, straight copy.

Not taking

  • Next.js / tRPC / Prisma as the app framework — the dashboard is Vite + Supabase.
  • Organization or Property.userId tenancy — everything keys on entity_slug.
  • Either project's auth — Supabase Auth is already the identity system for GCR.
  • OpenSyte's HR, payroll and project modules — not what we sell.
  • RentTools' passport/visa OCR — built for international rentals; irrelevant for Gulf Coast domestic guests.

Build order

  1. Lodging module (RentTools): consolidate the duplicate iCal feed tables, add buffers + platform defaults + the dedupe index, then cleaning, then guest forms. Independent of everything else, and serves 633 existing businesses.
  2. App framework (OpenSyte packaging): apps / app_versions / app_installs, reconciled with entity_modules.
  3. Workflow engine: the four-table port, triggered by app events.
  4. Direct booking + Stripe Connect — the actual answer to OTA fees, and the one thing neither project provides.

Every table above follows the house rule before it is applied: entity_slug column, RLS enabled, owner/admin write policy via owns_entity(), public read where GCR needs it, and an index on entity_slug.

sql/ownership_and_write_access.sql

Locks entity_owners, creates platform_admins and owns_entity(), adds owner-scoped write policies to 8 starter tables, and flags the open anon grants. Required before editing works.

sql/ownership_and_write_access.sql 172 lines 
-- ============================================================================
-- OWNERSHIP + WRITE ACCESS
--
-- Required before the dashboard's editing can be turned on safely.
--
-- The problem this solves: right now nothing links a login to a business.
-- entity_owners is empty, and the dashboard tracks the claimed slug in Supabase
-- user_metadata — which the browser can write. Without the pieces below, any
-- signed-up user can point themselves at any slug and edit or delete that
-- business's data.
--
-- Run this in the Supabase SQL editor. Read it first; it is written to be
-- reviewed, not pasted blindly.
-- ============================================================================


-- 1. Who owns what -----------------------------------------------------------
-- entity_owners already exists (id, user_id, entity_id, entity_slug, role).
-- Lock it down so a user cannot simply insert themselves as an owner.

ALTER TABLE public.entity_owners ENABLE ROW LEVEL SECURITY;

-- A user may read their own ownership rows, and nothing else.
DROP POLICY IF EXISTS entity_owners_read_own ON public.entity_owners;
CREATE POLICY entity_owners_read_own ON public.entity_owners
  FOR SELECT TO authenticated
  USING (user_id = auth.uid());

-- Deliberately NO insert/update/delete policy for regular users. Ownership is
-- granted out-of-band (service_role: an admin approval, verified invite email,
-- or phone verification). service_role bypasses RLS, so your backend can still
-- write these rows.

CREATE UNIQUE INDEX IF NOT EXISTS entity_owners_user_slug_uniq
  ON public.entity_owners (user_id, entity_slug);


-- 2. Platform admins ---------------------------------------------------------
-- Lets you open and edit any business's dashboard from the admin side.

CREATE TABLE IF NOT EXISTS public.platform_admins (
  user_id uuid PRIMARY KEY REFERENCES auth.users(id) ON DELETE CASCADE,
  note text,
  created_at timestamptz NOT NULL DEFAULT now()
);

ALTER TABLE public.platform_admins ENABLE ROW LEVEL SECURITY;

-- An admin can see their own row (that's how the dashboard knows). Nobody can
-- add themselves — grant admin with the service key or straight from the SQL
-- editor.
DROP POLICY IF EXISTS platform_admins_read_own ON public.platform_admins;
CREATE POLICY platform_admins_read_own ON public.platform_admins
  FOR SELECT TO authenticated
  USING (user_id = auth.uid());

CREATE OR REPLACE FUNCTION public.is_platform_admin()
RETURNS boolean
LANGUAGE sql
STABLE
SECURITY DEFINER
SET search_path = public
AS $$
  SELECT EXISTS (SELECT 1 FROM public.platform_admins WHERE user_id = auth.uid());
$$;

GRANT EXECUTE ON FUNCTION public.is_platform_admin() TO authenticated;

-- Admins need to browse the full business list in the picker.
DROP POLICY IF EXISTS entity_admin_read ON public.entity;
-- (entity is already publicly readable; no extra policy required.)


-- 3. The access test ---------------------------------------------------------
-- One function every write policy uses: you may change a business's data if you
-- own it, or if you are a platform admin.

CREATE OR REPLACE FUNCTION public.owns_entity(p_slug text)
RETURNS boolean
LANGUAGE sql
STABLE
SECURITY DEFINER
SET search_path = public
AS $$
  SELECT
    public.is_platform_admin()
    OR EXISTS (
      SELECT 1 FROM public.entity_owners
      WHERE user_id = auth.uid()
        AND entity_slug = p_slug
    );
$$;

GRANT EXECUTE ON FUNCTION public.owns_entity(text) TO authenticated;


-- 4. Turn on write access, table by table ------------------------------------
-- Apply to the tables a business should be able to edit. Deliberately explicit:
-- blanket-applying this to all 305 slug tables would also open booking records,
-- waivers, customer contact rows, and AI/internal tables to client writes.
--
-- Repeat this block per table. Start with a couple, confirm the dashboard
-- behaves, then widen.

DO $$
DECLARE
  t text;
  editable text[] := ARRAY[
    'entity_hours',
    'entity_photos',
    'menu_sections',
    'menu_items',
    'entity_events',
    'entity_specials',
    'faqs',
    'entity_policies'
    -- add more table names here as you decide to expose them
  ];
BEGIN
  FOREACH t IN ARRAY editable LOOP
    IF EXISTS (SELECT 1 FROM information_schema.tables
               WHERE table_schema='public' AND table_name=t) THEN

      EXECUTE format('ALTER TABLE public.%I ENABLE ROW LEVEL SECURITY', t);

      -- Public may keep reading (this is what GCR Unified relies on).
      EXECUTE format($p$
        DROP POLICY IF EXISTS %1$s_public_read ON public.%1$I;
        CREATE POLICY %1$s_public_read ON public.%1$I
          FOR SELECT USING (true);
      $p$, t);

      -- Owners may change only their own business's rows.
      EXECUTE format($p$
        DROP POLICY IF EXISTS %1$s_owner_write ON public.%1$I;
        CREATE POLICY %1$s_owner_write ON public.%1$I
          FOR ALL TO authenticated

-- Read-only helper for the business dashboard.
--
-- Returns every table in the database that is tied to a business slug and has
-- rows for it, as one JSON object keyed by table name. Adding a new table with
-- an entity_slug column makes it appear automatically — nothing is listed or
-- hardcoded anywhere.
--
-- SECURITY INVOKER: runs as the caller, so existing row-level security applies
-- exactly as it does today. This adds NO new data exposure. It only replaces
-- ~305 separate HTTP round trips with a single call.
--
-- Nothing existing is modified: this only adds one new function.

CREATE OR REPLACE FUNCTION public.entity_sections(p_slug text)
RETURNS jsonb
LANGUAGE plpgsql
STABLE
SECURITY INVOKER
SET search_path = public
AS $$
DECLARE
  result jsonb := '{}'::jsonb;
  t text;
  rows jsonb;
BEGIN
  FOR t IN
    SELECT DISTINCT col.table_name
    FROM information_schema.columns col
    JOIN pg_class c ON c.relname = col.table_name
    JOIN pg_namespace n ON n.oid = c.relnamespace AND n.nspname = 'public'
    WHERE col.table_schema = 'public'
      AND col.column_name = 'entity_slug'
      AND c.relkind = 'r'
    ORDER BY 1
  LOOP
    BEGIN
      EXECUTE format(
        'SELECT jsonb_agg(x) FROM (SELECT * FROM public.%I WHERE entity_slug = $1 LIMIT 500) x',
        t
      ) INTO rows USING p_slug;

      IF rows IS NOT NULL THEN
        result := result || jsonb_build_object(t, rows);
      END IF;
    EXCEPTION WHEN OTHERS THEN
      CONTINUE; -- an unreadable table must not break the whole response
    END;
  END LOOP;

  RETURN result;
END;
$$;

GRANT EXECUTE ON FUNCTION public.entity_sections(text) TO anon, authenticated;
